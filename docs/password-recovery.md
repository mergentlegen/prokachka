# Восстановление пароля

На экране входа появилась кнопка «Забыли пароль?». Участник вводит email, получает шестизначный код, подтверждает его и задаёт новый пароль. Затем входит обычным способом. Отправка кода не меняет пароль и не открывает кабинет.

## Что вручную настроить перед деплоем

1. В Supabase SQL Editor выполните **только** `supabase/20261003-password-recovery.sql`. Миграция предполагает, что `20261002-email-verification.sql` уже выполнена. Повторное выполнение новой миграции допустимо. Она не переносит аккаунты и не сбрасывает пароли при запуске.
2. В **Authentication → Emails → Templates → Reset password** (в интерфейсе также может называться Password recovery) установите тему `Восстановление пароля — Прокачка` и вставьте содержимое `supabase/templates/reset-password.html`. Шаблон Confirm sign up остаётся для регистрации. Код выводится через `{{ .Token }}`. Не обрезайте код в HTML.
3. В **Authentication → Sign In / Providers → Email** проверьте **Email OTP Length = 6**, **Email OTP Expiration = 600**. Уже подключённый SMTP Resend используется и для восстановления; дополнительных ключей не требуется.
4. Выложите изменения через обычный CI/CD. На сервере должен оставаться `AUTH_EMAIL_VERIFICATION_ENABLED=true`. Нового флага или перезапуска после изменения шаблона в Supabase не требуется.
5. Проверьте на отдельном тестовом аккаунте: неправильный код, правильный код, несовпадающие пароли, новый пароль и вход с ним. Старый пароль должен перестать подходить. В ранее открытом браузере старый вход должен потребовать повторной авторизации.

## Старые и новые аккаунты

Новые аккаунты меняют пароль через Supabase Auth. Для прежнего аккаунта при запросе создаётся, если необходимо, отдельная Auth-идентичность без передачи старого пароля и без выдачи доступа. Только после подтверждения владения почтой и успешной смены пароля существующий профиль связывается с этой идентичностью. UUID профиля, имя, команда, ветка, роль, Telegram, мили и звёзды сохраняются. Запрос восстановления для чужого адреса не связывает профили.

Системный CEO, который входит по серверным переменным, восстанавливается через настройки сервера; эта форма для участников и наставников с email. Адрес аккаунта должен быть доступен владельцу. При отсутствии доступа к почте автоматическое восстановление невозможно.

## Хранение и защита

- На запрос отправки всегда возвращается одинаковый ответ, независимо от существования адреса. Для неизвестного адреса аккаунт не создаётся.
- Код проверяется Supabase с назначением `recovery`. Коды регистрации не разрешают менять пароль.
- После проверки создаётся случайное разрешение на 10 минут: браузер получает только непрозрачную HttpOnly-cookie, в таблице хранится её SHA-256-хеш. Provider-сессия шифруется AES-256-GCM ключом, производным от существующего `AUTH_SECRET`. Пароли и коды в таблицах восстановления не сохраняются.
- Разрешение привязано к аккаунту и версии сессий. Оно используется один раз; одновременные запросы сериализуются короткой SQL-арендой. Ошибка требований к паролю разрешает повторить ввод, не запрашивая ещё одно письмо.
- Смена пароля повышает версию сессий и завершает прежние входы приложения. Проверка версии выполняется при чтении актуального пользователя и обновлении сессии.
- Ограничения адреса сохраняются между перезапусками: одна отправка в минуту, максимум пять за час и десять попыток кода за десять минут. Дополнительно действуют лимиты IP, Supabase Auth и почтового сервиса. Счётчики старше суток и истёкшие разрешения удаляются при последующих обращениях к восстановлению.
- В sessionStorage сохраняются только email, этап формы и время ожидания. Пароли, код и токены туда не попадают. Таблицы и SQL-функции доступны только серверной service-role.

При смене `AUTH_SECRET` открытые разрешения восстановления и существующие сессии станут недействительными. Изменение пароля в Supabase и завершение операции в PostgreSQL — две операции; при временном сбое завершения пользователь может повторить сохранение с действующим разрешением. Если разрешение уже истекло, нужно запросить новый код.
