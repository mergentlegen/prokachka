# Быстрое переключение разделов и live-обновления

## Поведение интерфейса

- Загруженный раздел показывается сразу из памяти. Свежесть ответа — 30 секунд; просроченные данные обновляются в фоне без скрытия страницы.
- Первое открытие незагруженного раздела показывает размытую заготовку карточек. Шапка, меню и заголовок остаются доступны. Искусственной секундной задержки нет.
- Наставник загружает данные выбранного раздела и небольшую сводку счётчиков. Участник на главной загружает объявления и рейтинг; задания, сеть и история профиля загружаются по необходимости.
- Одновременные одинаковые GET-запросы объединяются. Успешная мутация помечает зависимые данные устаревшими: открытый раздел обновляется, остальные перечитываются при переходе.
- Кэш хранится только в памяти вкладки. Выход, смена аккаунта, команды, прав или области сети очищают его. Поздние ответы из прежней области доступа отбрасываются.
- Фоновое обновление не закрывает формы и не размывает уже загруженные данные. Ошибка обновления сохраняет последний успешный результат и даёт кнопку повторной попытки.

## Схема уведомлений

В проекте собственные cookie-сессии, поэтому браузеру не выдаётся Supabase service role и не открывается подписка на приватные строки БД.

1. Триггеры БД отправляют метаданные изменения в закрытый Broadcast-канал `prokachka:changes`. Это охватывает и записи через Telegram, и транзакционные RPC.
2. Один серверный WebSocket на процесс Next.js получает события и распределяет сигналы между подключёнными браузерами.
3. `/api/events` проверяет текущий аккаунт, фильтрует сигналы по команде и отправляет через SSE **только названия изменившихся наборов данных**, без идентификаторов других людей, текстов работ и секретов.
4. Браузер объединяет события за 250 мс и обновляет необходимые API-ответы. Каждый API заново проверяет права и доступную ветку сети; кэш не заменяет авторизацию.

Сигнал для команды может прийти и участнику соседней ветки, но содержимое этой ветки ему не передаётся: API продолжает ограничивать данные. Это намеренно консервативная инвалидация, чтобы переносы в глубокой сети не оставляли старый доступ в интерфейсе.

При обычном соединении страховочная сверка выполняется раз в 120 секунд, при недоступном realtime — раз в 30 секунд. Скрытая вкладка закрывает SSE и приостанавливает эти проверки. При возвращении/восстановлении сети выполняется сверка. Запросы, начатые до скрытия вкладки, могут завершиться.

Heartbeat — раз в 20 секунд; зависшее соединение переподключается с увеличивающейся задержкой. Каждые 5 минут SSE открывается заново с проверкой текущих прав. При событии изменения доступа — раньше. Сбой Broadcast не отменяет сохранение работы: остаётся страховочное обновление.

Это near-realtime, а не гарантия нулевой задержки. Скорость зависит от связи, API и лимитов Supabase. Частых HTTP-запросов становится меньше; взамен появляются постоянные SSE-соединения, серверный WebSocket и небольшие события БД. Конкретное снижение нагрузки нужно измерять на реальном трафике.

Механизм: [Supabase Database Broadcast](https://supabase.com/docs/guides/realtime/broadcast), [Realtime authorization](https://supabase.com/docs/guides/realtime/authorization).

## Включение на рабочем сервере

Изменения подготовлены локально. Эта инструкция **не означает, что миграция или настройки сервера уже применены**.

1. Сделайте резервную копию БД. Убедитесь, что применено предыдущее обновление `20260917-architecture-integrity.sql`.
2. В Supabase SQL Editor выполните **только** `supabase/20260919-live-updates.sql`. Не запускайте `schema.sql`, `bootstrap.sql` или файлы из `tests/` на рабочей базе.
3. Миграция проверяет наличие `realtime.send`, создаёт триггеры и запрещает `anon`/`authenticated` читать или отправлять сообщения в зарезервированный канал. Серверный service role использует свой привилегированный доступ. Публичные RLS-политики добавлять не надо; публикация `supabase_realtime` для Postgres Changes не требуется.
4. Загрузите согласованные изменения кода через Git, выполните `npm ci`, `npm run build`, перезапустите существующий процесс приложения. Новые env-секреты не нужны: используются действующие серверные Supabase-настройки. Cron доставки Telegram не меняется.
5. Для Nginx добавьте в **существующий HTTPS server-блок** отдельный location. Адрес upstream замените на фактический порт приложения:

```nginx
location = /api/events {
    proxy_pass http://127.0.0.1:3000;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header Connection "";
    proxy_buffering off;
    proxy_cache off;
    gzip off;
    proxy_read_timeout 360s;
}
```

Не заменяйте весь конфиг этим фрагментом. Сохраните действующие TLS-настройки и остальные location-блоки. Перед reload выполните `sudo nginx -t`; только при успешной проверке — `sudo systemctl reload nginx`. При наличии CDN/дополнительного прокси исключите `/api/events` из буферизации и кэширования там тоже.

Сервер должен поддерживать длительные HTTP-соединения. Для текущего VPS/Node-процесса это штатный сценарий; при переезде на serverless проверьте ограничения времени исполнения и числа соединений отдельно.

### Проверка после выкладки

1. Откройте наставника и участника в разных браузерных профилях. В Network у авторизованной страницы `/api/events` должен отвечать `200`, `text/event-stream`, оставаться открытым и выдавать `ready` и heartbeat. Состояние `pending` у такого запроса нормально. `401` без авторизации — тоже нормально.
2. Загрузите «Задания», перейдите в «Историю», вернитесь в «Задания»: меню не исчезает, повторного загрузочного экрана нет. В пределах 30 секунд неизменённые общие данные не запрашиваются повторно.
3. Отправьте работу тестового участника через Telegram. У наставника должны обновиться очередь/счётчик. Примите работу — у участника изменятся статус, история профиля и рейтинг без F5.
4. Выдайте тестовую награду; проверьте сумму звёзд. Опубликуйте тестовое задание/объявление; проверьте соответствующий открытый раздел в разрешённой ветке.
5. Измените тестовому участнику права или положение в сети. Недоступные данные должны исчезнуть; доступные — загрузиться заново. Проверьте, что другая команда не получает чужое содержимое.
6. Отключите сеть и восстановите: интерфейс не должен сбрасываться; после восстановления данные догружаются. В скрытой вкладке не должно быть постоянных новых запросов.

Если приходят только `degraded`, проверьте доступ сервера к Supabase Realtime и service role. Если `ready` есть, но при действиях нет `change`, проверьте применение миграции, триггеры и ограничения Realtime. Если события приходят пачкой с большой задержкой — проверьте буферизацию прокси. Без миграции возможен `ready` транспорта без событий БД: останется только резервный опрос.

## Локальные проверки

`npm run check` проверяет TypeScript, ESLint, unit/component-тесты и production-сборку. В `tests/live-updates.test.cjs` проверяются кэш, гонки ответов, жизненный цикл разделов, изоляция сессий, фильтрация SSE, восстановление связи и общий серверный канал.

В одноразовом PostgreSQL без Supabase сначала выполняется `tests/realtime-fixture.sql`, затем bootstrap/миграция и `tests/live-updates.sql`. Fixture заменяет только транспорт `realtime.send` транзакционной тестовой таблицей. Проверяются метаданные, INSERT/UPDATE/DELETE, откат транзакции, RLS закрытого канала и сохранение бизнес-операции при сбое доставки. Это не проверка внешней инфраструктуры Supabase.

Для ручной проверки UI без рабочей БД:

```sh
npm run build
npm start -- --port 3105 --hostname 127.0.0.1
# В другом терминале:
node tests/helpers/ui-fixture-server.cjs
```

Откройте `http://127.0.0.1:3106/admin` и `http://127.0.0.1:3106/`. Этот локальный proxy перехватывает **все** `/api/*`, подставляет вымышленные данные и запрещает немокированные API; только страницы/ассеты идут к локальному Next. Он слушает loopback, не предназначен для production. `/__test/stats` показывает счётчики запросов; POST `/__test/change` имитирует событие изменения рейтинга. Завершите оба процесса после проверки.

Автоматические проверки не заменяют визуальную проверку iPhone/Safari и двух аккаунтов на настроенном production-сервере.
