# Аудит безопасности — 28 сентября 2026

## Что проверено и где заканчиваются гарантии

Проверен код репозитория: регистрация, вход, подтверждение почты, восстановление пароля,
cookie-сессии, административные действия, изоляция команд/веток, задания/игры/награды,
загрузки PDF и аватаров, выдача приветственного видео, Telegram webhook, SSE,
SQL-права и миграции, сборка и публикация релизов, зависимости npm.

SQL и конкурентные запросы проверены на **отдельном локальном PostgreSQL 17** с
Supabase-совместимыми тестовыми схемами. Рабочая база не изменялась. Браузерные тесты
использовали подставные API: реальные аккаунты не создавались, письма не отправлялись.
На production выполнен только обычный HEAD-запрос главной страницы: HTTP 200,
HTTPS, HSTS, CSP, nosniff и запрет встраивания страницы присутствуют.

Это аудит исходников и автоматические проверки, а не независимый внешний пентест.
Состояние VPS, firewall/SSH, реальные политики Supabase, настройки SMTP/Auth, история
секретов в Git, права сотрудников и защита от объёмного DDoS не были проверены.
Отсутствие выявленных ошибок не является гарантией отсутствия всех уязвимостей.

Новая таблица лимитов хранит SHA-256 нормализованного email, начало окна и счётчик,
**не пароль и не код**. Это не анонимизация: email можно проверять перебором хэшей.
Доступ к таблице закрыт для клиентов. При входах удаляется до 100 записей старше суток;
при полном отсутствии входов старые строки останутся до следующего вызова.
Счётчик учитывает все попытки, включая успешные. Блокировка временная и не продлевается
каждой отклонённой попыткой. Восстановление пароля имеет отдельный лимит.

## Пароли

- При регистрации и установке нового пароля: минимум 8 символов, заглавная латинская
  или русская буква и цифра. Спецсимвол не обязателен. Максимум — 1 024 символа.
- Одна общая политика используется формой, контроллером и сервисами регистрации/сброса.
  Обход JavaScript-проверки не позволяет сохранить слабый новый пароль через API сайта.
- Под полем показана понятная подсказка; ошибки связаны с полем для экранного диктора.
- Старые пароли остаются пригодными для входа. Насильственный сброс всем пользователям
  не выполнялся. Для повышения безопасности существующим пользователям нужно сменить
  слабые пароли; администраторам рекомендуется уникальный длинный пароль и MFA.

8 символов с составом — требование владельца, а не максимальная защита. Современные
рекомендации делают акцент на длине, проверке утёкших паролей и MFA, а не только на
наличии разных типов символов: [OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html).

## Подтверждённые существующие защитные механизмы

- HttpOnly/Secure/SameSite cookie; секрет подписи не передаётся браузеру.
- Сброс пароля требует проверенного recovery-кода и одноразового серверного grant;
  токены провайдера зашифрованы; после сброса повышается версия сессии.
- Проверки принадлежности к команде/ветке и авторства публикации выполняются на сервере;
  начисление игровых миль не доверяет числу, присланному клиентом.
- Telegram webhook проверяет секрет и личный чат; повторные события и гонки проверены SQL-тестами.
- Аватары повторно декодируются/перекодируются сервером; лимит пикселей ограничен,
  исходные EXIF/GPS-данные не сохраняются в итоговой картинке.
- Приватные файлы доступны через проверенные сервером маршруты/ограниченные ссылки.
- На тестовой актуальной схеме у `anon`/`authenticated` нет прямых CRUD-прав на таблицы
  приложения. Единственная разрешённая SECURITY DEFINER-функция —
  `welcome_video_upload_path_allowed`, проверяющая временное разрешение на конкретный путь.

## Обязательно перед выкладкой

1. Создать/проверить резервную копию БД. В Supabase SQL Editor применить **только**
   `supabase/20261008-security-hardening.sql`. Не запускать `schema.sql` или `bootstrap.sql`
   на существующей базе. Миграция добавляет счётчик входов и защитные настройки,
   не удаляет аккаунты, задания, результаты или файлы.
2. Выполнить `supabase/security-status.sql` — это read-only проверка. Ожидание:
   RLS включён, anon/authenticated CRUD = false; новый RPC установлен; CREATE = false;
   единственная открытая привилегированная функция описана выше. Несовпадения сначала
   разобрать, а не выдавать широкие права ролям.
3. После миграции выложить код обычным CI/CD. **Без миграции новые входы вернут 503**:
   код намеренно не отключает защиту, если счётчик недоступен. Уже открытые валидные
   сессии продолжат работать. Системному CEO потребуется один повторный вход.
4. Проверить реальные настройки Supabase Auth: Confirm email включён, минимальная
   длина пароля не меньше 8, проверка утёкших паролей включена, лимиты отправки/OTP
   настроены. Провайдерская политика не менялась автоматически; API провайдера
   доступен отдельно от API сайта. Параметры длины/состава должны быть согласованы
   с приложением: [Supabase password security](https://supabase.com/docs/guides/auth/password-security).
5. На VPS: `AUTH_DEV_MODE=false`, случайный `AUTH_SECRET` минимум 32 символа,
   `NEXT_PUBLIC_APP_URL=https://prokachka.kz`, секрет service role только на сервере,
   сильный уникальный `CEO_PASSWORD`. Next слушает `127.0.0.1`, а не публичный порт.
6. Проверить Nginx: он должен **перезаписывать** `X-Real-IP` реальным адресом клиента,
   а не доверять присланному заголовку. За CDN сначала настраивается real_ip только
   для доверенных адресов CDN. Нужны серверные лимиты тела/времени запроса и соединений.
   В приложении самый большой проксируемый upload — multipart PDF до 16 MiB;
   приветственное видео загружается напрямую в Storage, поэтому не требует огромного
   `client_max_body_size` на VPS.
7. После выкладки: новый пароль `Abcdefg1` принимается, `abcdefg1`/`ABCDEFGH`/`Abcd12`
   отклоняются; старый аккаунт входит; сброс пароля работает; проверка роли и чужой
   ветки не открывает данные. Тест лимита входов проводить только своим тестовым
   аккаунтом, не блокируя реальных пользователей.

## Остаточные риски и дальнейшие решения

- MFA для приложения, особенно CEO/наставников, пока нет. MFA в аккаунте Supabase/GitHub
  защищает их панели, но **не заменяет** MFA при входе на сайт.
- Текущий logout удаляет cookie браузера, но не отзывает отдельную ранее скопированную
  cookie на сервере. Сброс пароля отзывает сессии по версии; для точечного отзыва,
  списка устройств и абсолютного срока сессий нужен отдельный реестр сессий.
- CSP ещё разрешает inline scripts, необходимые текущей статической сборке Next.
  Произвольного выполнения пользовательского HTML в проверенных компонентах не найдено,
  однако это не строгая CSP. Переход на nonce требует динамического рендеринга и отказа
  от кэширования HTML; его нужно внедрять и тестировать отдельно, не удаляя
  `unsafe-inline` вслепую. JS/CSS/изображения при таком переходе могут остаться в CDN.
  Основание: локальная документация установленного Next.js,
  `node_modules/next/dist/docs/01-app/02-guides/content-security-policy.md`.
- Временная signed URL — bearer-ссылка: получивший её сможет скачать файл до истечения
  срока. Это не DRM и не запрет пересылки/записи экрана. Смена прав проверяется при
  получении новой ссылки, а не при каждом CDN-запросе старой.
- От вредоносного содержимого PDF нет антивирусного сканера. Проверка типа/размера,
  права и браузерный sandbox не заменяют AV/CDR при приёме файлов от недоверенных авторов.
- Лимит БД ограничивает подбор одного аккаунта между процессами; IP-лимиты и SSE-бюджеты
  остаются локальными процессу. Для большой распределённой установки нужен edge/WAF
  либо Redis-лимитер; приложение не способно само остановить сетевой DDoS.
- Ответ о существующем email при регистрации сохранён ради текущего UX. Это позволяет
  определять наличие аккаунта; единообразный ответ потребует изменения сценария регистрации.
- Безопасность production зависит от применения всех прежних миграций, закрытых bucket,
  доступов к VPS/Supabase/GitHub/Resend, резервных копий и регулярных обновлений.
  Эти настройки не следует считать проверенными только по успешным локальным тестам.

Изменения не закоммичены, не отправлены в GitHub и не применены к production автоматически.
