# Подтверждение почты при регистрации

Восстановление пароля описано отдельно: [password-recovery.md](password-recovery.md).

## Что изменилось

Новые участники вводят имя, фамилию, email и пароль, затем шестизначный код из письма. Только после подтверждения создаётся профиль приложения и заявка наставнику по приглашению. Подтверждение почты не принимает участника в команду: наставник одобряет заявку отдельно. Дальнейший вход — email + пароль, без письма при каждом входе.

Supabase Auth проверяет новые пароли и коды. Приложение по-прежнему выдаёт свою HttpOnly-сессию и читает актуальные роли/ветки из `public.users`. Токены Supabase не отправляются в браузер. Это поэтапное подключение Auth, не полная замена системы сессий. Существующие пользователи остаются на текущем входе, с прежними UUID, паролями, командами, Telegram и милями; автоматического связывания аккаунтов по совпадению email нет.

SMTP отправляет сам Supabase, поэтому SMTP-пароль не нужен ни в GitHub Secrets, ни в `.env` приложения. Один клиент Supabase с публичным ключом создаётся на каждую проверку; административный service-role клиент никогда не используется для входа пользователя.

## Порядок включения — важно

Не включайте `AUTH_EMAIL_VERIFICATION_ENABLED=true`, пока не настроены миграция, SMTP, Confirm Email и шаблон кода. Рекомендуемый порядок: новая миграция, затем код, затем включение функции. Пока flag выключен, существующий вход продолжает работать и до миграции. При включённом flag отсутствие миграции блокирует вход безопасной ошибкой, не обходом подтверждения.

### 1. Примените только новую миграцию

В Supabase откройте **SQL Editor**, создайте новый запрос и вставьте всё содержимое:

`supabase/20261002-email-verification.sql`

Нажмите **Run**. Миграция добавляет колонку, приватные черновики и серверные функции. Она не меняет старые пароли или аккаунты. Повторное выполнение этой конкретной миграции допустимо. **Не запускайте `schema.sql`, `bootstrap.sql` или файлы из `tests` в рабочей базе.**

### 2. Зарегистрируйтесь в сервисе отправки писем

Пример настройки — [Resend](https://resend.com). Можно выбрать другой сервис с SMTP; код приложения от этого не меняется.

В Resend откройте **Domains → Add domain**, добавьте `auth.prokachka.kz`. Это отдельный поддомен для служебных писем, сайт остаётся на `prokachka.kz`.

### 3. Подтвердите домен через DNS

Resend покажет записи для вашего домена. В кабинете, где управляются DNS `prokachka.kz`, добавьте **точно те значения**, которые показаны Resend. Обычно это TXT для DKIM/SPF и MX для служебного адреса обработки доставки.

Не меняйте A/AAAA записи сайта и существующие MX основной почты. Не добавляйте два SPF TXT на одно и то же имя: если SPF уже есть именно на указанном имени, настройки нужно объединить по инструкции сервиса. DNS-кабинет может сам дописывать `.prokachka.kz` к имени записи — не допускайте повторения домена.

Добавьте DMARC для отправляющего поддомена: TXT с полным именем `_dmarc.auth.prokachka.kz` и значением `v=DMARC1; p=none;`. Это начальный режим наблюдения, не запрет доставки. Если запись уже существует, не создавайте вторую. Более строгую политику включайте после проверки отправки.

Вернитесь в Resend и дождитесь статуса **Verified**. SPF/DKIM/DMARC повышают доверие к отправителю, но не гарантируют отсутствие спама. Отдельный принимающий ящик `no-reply@auth.prokachka.kz` для отправки не обязателен.

### 4. Подключите SMTP к Supabase

В Resend создайте API key с правом отправки для подтверждённого домена. Сохраните его в менеджере паролей — не отправляйте ключ в чат и не коммитьте.

В Supabase откройте **Authentication → Email → SMTP Settings** (названия разделов могут меняться), включите custom SMTP и заполните:

| Поле | Значение |
| --- | --- |
| Sender email | `no-reply@auth.prokachka.kz` |
| Sender name | `Прокачка` |
| Host | `smtp.resend.com` |
| Port | `465` |
| Username | `resend` |
| Password | ваш API key Resend |

Сохраните. Это подключение готового сервиса, а не установка почтового сервера на Ubuntu. Платёжный тариф и лимиты Resend выбирайте под вашу фактическую нагрузку отдельно от Supabase Pro.

### 5. Настройте регистрацию в Supabase Auth

В настройках Auth:

- Email provider — включён.
- Email/password sign-up — разрешён.
- **Confirm Email — обязательно включён.** Если он выключен, приложение не выдаёт доступ и возвращает ошибку конфигурации.
- OTP length — **6**.
- Email OTP expiry — **600 секунд** (10 минут).
- Minimum interval between emails — **60 секунд**.
- Site URL — `https://prokachka.kz`.
- Проверьте общую квоту отправки в **Rate Limits** и квоту почтового сервиса. При custom SMTP Supabase изначально может ограничивать отправку 30 письмами/час; настройте лимит под реальную регистрацию, не безгранично.
- Сохраните текущий минимум пароля 6 символов, либо синхронно измените требования фронта/бэка перед увеличением. Не меняйте это только в dashboard.

При публичной рекламе регистрации отдельно подключите CAPTCHA и передачу её токена в Auth. В этой версии CAPTCHA не добавлена: действуют ограничения IP, адреса и Supabase. Прямой Auth endpoint также публичный, поэтому защита только нашего `/api` не заменяет лимиты Supabase.

### 6. Поставьте шаблон письма с кодом

**Authentication → Email Templates → Confirm sign up**. Тема: `Код подтверждения почты — Прокачка`.

Вставьте содержимое `supabase/templates/confirm-signup.html`. Важно: код берётся из `{{ .Token }}`, а не из `{{ .ConfirmationURL }}`. Меняйте именно **Confirm sign up**, а не Magic Link: пользователь регистрируется с паролем.

Шаблон содержит только код и инструкцию, без рекламы, внешних картинок или параметров пользователя. В Supabase установленный срок действия должен совпадать с указанными в письме 10 минутами.

### 7. Выложите изменения, пока функция ещё выключена

После миграции сделайте коммит и push в `main`, дождитесь успешного CI/CD. Проверьте вход существующего аккаунта.

Пример сообщения коммита:

`feat email signup verification with Supabase Auth`

Ни коммит, ни push, ни рабочая миграция автоматически не выполнялись.

### 8. Включите функцию на сервере

На Ubuntu:

```bash
sudo nano /var/www/prokachka/.env.production
```

Сохраните существующие настройки и добавьте/измените **одну** строку:

```dotenv
AUTH_EMAIL_VERIFICATION_ENABLED=true
```

Также должны быть заполнены `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `AUTH_SECRET` и `NEXT_PUBLIC_APP_URL=https://prokachka.kz`. Не выводите их значения в чат. Публичный ключ берётся из того же проекта Supabase, что URL и service-role ключ. В проекте уже используются эти настройки; заменять существующие ключи не нужно.

В nano: **Ctrl+O**, **Enter**, **Ctrl+X**. Затем:

```bash
sudo systemctl restart prokachka.service
sudo systemctl status prokachka.service --no-pager
```

Flag читается сервером во время запуска, не требует отдельного GitHub Secret или пересборки при изменении только этой строки. SMTP-пароль хранится в Supabase, не на Ubuntu.

### 9. Проверьте весь сценарий

Используйте настоящий **новый** email, желательно сначала Gmail, затем второй почтовый сервис.

1. Откройте действующую ссылку приглашения и зарегистрируйтесь.
2. До кода кабинет не должен открываться, заявка наставнику не должна появляться.
3. Введите неверный код — ошибка должна оставаться возле поля.
4. Через 60 секунд попробуйте повторную отправку; используйте код из последнего письма.
5. Обновите страницу — шаг кода сохранится в этой вкладке. В браузере хранится только email и время повторной отправки, не пароль/код/токены.
6. Введите правильный код — появится профиль и одна заявка наставнику, но членство не одобряется автоматически.
7. После принятия в команду проверьте кабинет, выйдите и войдите снова по почте и паролю.
8. Проверьте существующего участника и наставника: команды, мили, роли и аватарки должны сохраниться.

Если подтверждение прошло, но сервер временно не смог создать профиль, повторный вход по email/паролю завершает создание идемпотентно. Повторное использование уже погашенного кода не требуется.

## Ошибки и ограничения

- 429: слишком много попыток; ответ содержит `Retry-After`. Проверки: 10 кодов за 10 минут на адрес; отправка не чаще минуты, до 5 писем/час на существующий черновик. Дополнительно действуют IP-ограничения API и лимиты Supabase.
- 503 отправки: проверяйте **Supabase Auth Logs** и **Resend Emails**, Verified домен, SMTP key, лимиты. Приложение не раскрывает SMTP ошибки/секреты пользователю.
- Вход не работает после выкладки: сначала проверьте, применена ли миграция с `auth_user_id`.
- Если приглашение истекло между регистрацией и подтверждением, подтверждённый аккаунт сохраняется, но заявка по недействительному приглашению не создаётся. Команду можно выбрать вручную.
- Старые аккаунты не становятся подтверждёнными в Supabase и не мигрируют автоматически. Их перенос и восстановление пароля через Supabase — отдельный следующий этап. Новый интерфейс «Забыли пароль» в эту задачу не включён.
- Приватные черновики удаляются после успешного завершения; незавершённые регистрации остаются для повторного входа. Автоматическая очистка незавершённых Auth-аккаунтов не настроена: нельзя удалять их без согласованного срока хранения.
- Отключение flag вернёт старую регистрацию без подтверждения; это не безопасный режим защиты почты. Уже созданные Supabase-аккаунты всё равно проверяют пароль через Supabase, без fallback на старый hash. Для аварии почтового сервиса предпочтительнее временно закрыть новую регистрацию, а не снимать подтверждение.

## Проверки разработчика

`npm test`, `npm run typecheck`, `npm run lint`, `npm run build`.

SQL: в отдельной пустой тестовой базе загрузить `tests/database-roles.sql`, `tests/realtime-fixture.sql`, `tests/storage-fixture.sql`, `tests/auth-fixture.sql`, затем `supabase/bootstrap.sql` и `tests/email-auth.sql`. Тест проверяет неподтверждённые/заблокированные аккаунты, отсутствие автослияния старого email, приглашения, идемпотентность, лимиты и права. Auth-fixture — только минимальная модель каталога для SQL, не тест настоящей доставки писем.

Опциональная проверка браузером: запустить собранное приложение на `127.0.0.1:3107`, указать `PROKACHKA_PLAYWRIGHT_MODULE` (установленный Playwright) и временную `PROKACHKA_UI_ARTIFACT_DIR`, затем `node tests/email-auth-ui.cjs`. Все API и внешние запросы перехватываются тестом; реальных писем и записей не создаётся. Параллельные проверки находятся в `tests/telegram-concurrency.test.cjs` и запускаются только с портом отдельной тестовой PostgreSQL.

Официальные инструкции: [SMTP Supabase](https://supabase.com/docs/guides/auth/auth-smtp), [Resend + Supabase](https://resend.com/docs/send-with-supabase-smtp), [шаблоны писем](https://supabase.com/docs/guides/auth/auth-email-templates).
