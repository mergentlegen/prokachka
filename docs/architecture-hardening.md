# Архитектурное обновление 17.09.2026

## Что изменилось

- `backend/http/current-user.ts` читает актуальные права из БД один раз на HTTP-запрос. Старые права в cookie не дают прежний доступ после снятия роли или команды.
- Рейтинг использует явную область доступа: команда или все команды для CEO. SQL суммирует все записи, API читает результат страницами, включая участников с нулём миль. Звёзды остаются накопительными.
- Создание программы вместе с шагами, обновление сроков, рассмотрение заявки и смена руководителя с историей выполняются транзакционно.
- Назначение команды в CEO-панели закрывает ожидающие заявки в той же транзакции. Отдельная незащищённая RPC одобрения больше недоступна серверной роли.
- Структурные изменения пользователей сериализованы короткой advisory-блокировкой: параллельные перестановки не создают циклы.
- Перенос участника с подчинёнными запрещён до переподчинения детей. Весь нижний состав не переносится без явного решения.
- Удаление пользователя, ограничивающего аудиторию публикации, блокируется внешним ключом. Материал не становится общекомандным из-за `SET NULL`. Для такого удаления сначала нужна осознанная смена аудитории через отдельную административную процедуру; нового интерфейса для неё пока нет.
- Панель наставника разделена на контейнер, экраны, формы и хук загрузки. Данные загружаются по открытому разделу; счётчики — отдельным небольшим запросом. Рейтинг панели использует тот же API, что и рейтинг участников.
- DTO истории находятся в `shared/domain/history.ts`, а не импортируются UI из backend. История использует индексы ответов и учитывает аудиторию программы.
- Удалены неиспользуемые `frontend/shared/demo-data.ts`, `frontend/shared/storage/store.ts` и мёртвые функции. Удалённые файлы доступны в Git.

## Обновление существующей базы

Не запускайте `schema.sql` или `bootstrap.sql` поверх рабочей базы. Исторические миграции сохранены намеренно.

1. Сделайте резервную копию базы и запишите текущую версию приложения.
2. Убедитесь, что ранее применены `telegram-integrity-migration.sql` и `star-award-kinds-migration.sql` (см. соседние инструкции).
3. Проверьте межкомандные связи запросом ниже. Если есть строки, сначала согласуйте, кому должны подчиняться эти люди. Миграция сама их не переносит.
4. Подготовьте новую сборку командой `npm ci`, затем `npm run check`.
5. На время переключения остановите приём изменений в приложении. Примените **весь** `supabase/20260917-architecture-integrity.sql` в SQL Editor Supabase или через `psql -X -v ON_ERROR_STOP=1 -f supabase/20260917-architecture-integrity.sql` с подключением к нужной базе.
6. Только после успешной миграции запустите новую сборку. Новые API требуют новых RPC; старая версия после отзыва старой RPC не сможет принимать заявки.
7. Проверьте рейтинг обычного участника и наставника, выдачу прав, заявку, программу с несколькими шагами и Telegram-доставку. Настройки уже работающего cron не меняются.

```sql
select child.id, child.name, child.team_id, child.parent_user_id,
       parent.team_id as parent_team_id
from public.users child
join public.users parent on parent.id = child.parent_user_id
where child.team_id is distinct from parent.team_id or child.team_id is null;
```

Миграция обёрнута в `BEGIN/COMMIT`: при ошибке прекратите обновление приложения и выясните причину. Старые ответы, звёзды и заявки она не удаляет. Повторное применение допустимо. Автоматического отката схемы нет: откат приложения и базы нужно согласовывать вместе; не возвращайте старый доступ к RPC без проверки безопасности.

## Новая база и проверки

Для новой **пустой** базы `supabase/bootstrap.sql` задаёт порядок файлов. Он предназначен для `psql` и содержит команды `\ir`, поэтому не подходит для вставки целиком в SQL Editor. В Supabase роли уже существуют; `tests/database-roles.sql` нужен только в одноразовом локальном PostgreSQL/CI. После добавления realtime для локального PostgreSQL перед bootstrap нужен `tests/realtime-fixture.sql`; в рабочий Supabase тестовые fixture-файлы не загружать. См. [обновление realtime](live-updates.md).

```sh
npm run lint
npm run typecheck
npm test
npm run build
```

`npm run check` объединяет эти четыре проверки. Unit-тесты не используют секреты приложения или рабочую БД.

ESLint проверяет Next.js и React. Существующие рекомендации по полной навигации, изображениям и подготовке к React Compiler пока остаются предупреждениями, а нарушения порядка хуков — ошибками. Это не означает, что весь старый UI уже переработан. ESLint 9 выбран по совместимости peer-зависимостей текущих `eslint-plugin-react`/`jsx-a11y`; переход на поддерживаемую новую major-версию нужно делать вместе с совместимыми версиями этих плагинов, без `--force`.

SQL-проверки выполняйте только в одноразовой тестовой базе после bootstrap:

```sh
psql -X -v ON_ERROR_STOP=1 -f tests/telegram-integrity.sql
psql -X -v ON_ERROR_STOP=1 -f tests/architecture-integrity.sql
PROKACHKA_TEST_PG_PORT=5432 npm run test:concurrency
```

Укажите параметры подключения `PGHOST/PGPORT/PGUSER/PGDATABASE/PGPASSWORD` для SQL-файлов. Конкурентные тесты намеренно подключаются только к `127.0.0.1`, пользователю `postgres` и БД `postgres`; порт обязателен, иначе тесты пропускаются. Они оставляют UUID-fixtures в тестовой базе. Приложение `.env` не читают. CI запускает собственный контейнер PostgreSQL 17.

## Следующие отдельные этапы

- Курсорная пагинация HTTP/UI для больших историй и виртуализация длинных списков. Сейчас чтение страниц из Supabase предотвращает обрезание данных, но итоговые массивы всё ещё могут быть большими.
- Дальнейшее разделение `MemberApp`, `CEOApp` и глобального CSS с визуальными регрессионными тестами. В этом обновлении внешний вид намеренно не переработан.
- Унификация поведения всех модальных окон и полноценные браузерные end-to-end тесты. Unit/SQL-проверки не заменяют проверку реального Safari и production-конфигурации.
- Версионированный migration runner для автоматического учёта применённых миграций. Сейчас порядок документирован и проверяется bootstrap в CI; накатывать базовый schema повторно нельзя.
