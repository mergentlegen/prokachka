# Приветственные видео: Pro, CDN и очистка

## Что меняется

MP4 до **200 МиБ**, до 3 минут, любая ориентация; приватный бакет `welcome-videos`.
Для приятного просмотра и экономии рекомендуются 1080p, H.264/AAC, 3–5 Мбит/с,
«fast start / оптимизация для веба». Три минуты обычно занимают около 60–120 МБ.
Загрузка **не перекодирует** видео: 4K или большой исходник нужно сжать перед загрузкой.
Хранится один оригинал, без создания нескольких копий/вариантов качества.

Участник получает видео ближайшего издателя выше по своей ветке; если нет — видео
корневого наставника команды. Соседние команды/ветки не получают чужую ссылку через API.
После завершения onboarding в БД остаётся отметка, и файл больше не загружается
при следующих входах. Замена видео не сбрасывает эту отметку.

Стандартный плеер поддерживает звук, паузу и полный экран, показывает постер и буферизацию.
Позиция сохраняется локально раз в 5 секунд, при паузе/уходе со страницы, не более 7 дней.
Позиция привязана к пользователю и версии файла, не переносится на заменённое видео.
Прогресс не синхронизируется между устройствами; факт завершения — синхронизируется через БД.
При ошибке сохранения можно повторить сохранение, не пересматривая видео.

## Как работает кэш

На Pro Smart CDN включён Supabase автоматически. Байты передаются напрямую из Storage/CDN,
не через Next.js/Nginx сайта. Новые файлы всегда получают новый UUID-путь: нет устаревшей
версии по прежнему адресу. Нативный плеер использует Range-запросы и `preload="metadata"`,
без предварительной загрузки всего файла, autoplay и дубля видео в service worker.

Уникальный токен signed URL — отдельный ключ CDN. Поэтому приватная служебная таблица
хранит общую ссылку **для одного файла** на 5 часов; токен выдан на 6 часов. Первые конкурентные
запросы сходятся к одной канонической ссылке через SQL RPC. При каждом запросе заново
проверяются текущий аккаунт, команда, завершение просмотра и цепочка наставников.
Ответ API имеет `Cache-Control: private, no-store`; кэшируется файл, не права пользователя.
Браузерный TTL файла — 1 час. Пустые/просроченные записи URL-кэша удаляет worker.

Signed URL — bearer capability: получатель технически может скопировать ссылку.
Истечение токена **не гарантирует** немедленное удаление уже тёплой копии из CDN.
Для отзыва самого видео удаляется объект через Storage API; инвалидирование CDN обычно
занимает до минуты. Уже скачанное пользователем отозвать нельзя. Бакет остаётся приватным.
Это не DRM и не обещание, что кэшированный трафик бесплатен: он учитывается отдельно.
Проверять реальные cache hits нужно в статистике Supabase Storage/CDN.

## Обновление существующего проекта — один раз

1. В Supabase SQL Editor выполнить **только** `supabase/20260930-welcome-video-pro.sql`.
   Ранее применённые welcome-миграции, `schema.sql` и `bootstrap.sql` не повторять.
   Новая миграция повторяемая, не сбрасывает просмотр и не удаляет используемые видео.
2. В Supabase **Storage → Settings → Global file size limit** выставить не менее
   **200 МиБ (209715200 байт)**. Миграция меняет лимит бакета, но не глобальную настройку.
3. Закоммитить/запушить код в `main`, дождаться CI и успешного deployment.
   SQL применяется **до** нового backend: он использует новые служебные функции и таблицы.
   В рабочем env сервера нужен `NEXT_PUBLIC_SUPABASE_ANON_KEY` — только публичный anon/publishable
   ключ своего проекта, никогда service-role/secret key. Он выдаётся при запросе загрузки,
   не зависит от GitHub build-time variables. Service-role остаётся приватным на сервере.
4. Включить фоновый таймер очистки на сервере. Образцы unit-файлов лежат в `scripts/`.
   Сам worker включён в каждый CI/CD-пакет, дополнительных npm-пакетов не требует.

На Ubuntu по SSH (после нового деплоя):

```bash
sudo nano /etc/systemd/system/prokachka-video-cleanup.service
```

Вставить содержимое `scripts/prokachka-video-cleanup.service.example`.
Проверить **User/Group**, путь **EnvironmentFile** (тот же рабочий production env, что у сайта),
**/usr/bin/node** и **/var/www/prokachka-deploy/current** — они должны соответствовать серверу.
Не копировать секреты в unit и не создавать отдельный env для каждого релиза.

```bash
sudo nano /etc/systemd/system/prokachka-video-cleanup.timer
```

Вставить содержимое `scripts/prokachka-video-cleanup.timer.example`, затем:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now prokachka-video-cleanup.timer
sudo systemctl start prokachka-video-cleanup.service
sudo systemctl status prokachka-video-cleanup.timer --no-pager
sudo journalctl -u prokachka-video-cleanup.service -n 30 --no-pager
```

Без таймера удаление/замена убирает запись с сайта, но файлы остаются в очереди!
В логах показываются количества удалений/отложенных операций, без URL/токенов.
Если worker возвращает ошибку, проверить env, права service-role и применение миграции.

## Безопасная очистка

Триггеры транзакционно записывают старый путь при замене/удалении видео, включая каскадное
удаление аккаунта/команды. Worker каждые 10 минут забирает до 10 объектов с блокировкой
`SKIP LOCKED`, 5-минутной арендой и индивидуальным токеном подтверждения.
Рабочие файлы и незавершённые активные upload intents не выдаются на удаление.
Файлы удаляются **через Storage API**, никогда через SQL-delete `storage.objects`.
Ошибки сохраняются для повторной попытки с exponential backoff; успешные jobs удаляются.

Брошенные/отменённые загрузки очищаются после истечения их 2-часового разрешения
и ещё 24 часов защитного интервала для TUS. Незавершённые временные чанки TUS управляются
самим Supabase; очередь приложения удаляет объекты, а не внутренние чанки Storage.
Миграция также ставит в очередь старые осиротевшие MP4 в этом бакете с валидным UUID-путём.
Произвольные файлы других бакетов не затрагиваются. Удалённые старые видео восстановить
из очереди нельзя: для повторного использования понадобится исходный файл.

## Проверки

CI: тесты сервисов/worker/прогресса, bootstrap с новой миграцией, повторное применение миграции,
SQL-сценарии веток, чужой команды, отозванных прав, cache token reuse, замены, идемпотентного
finish, expired upload, cleanup lease/backoff, завершённого onboarding.
Конкурентные тесты отдельно проверяют шесть первых зрителей и четыре одновременные замены видео.
После production-обновления проверить новым тестовым участником своей и соседней ветки,
обновить страницу посередине просмотра и проверить запись завершения после просмотра.
